# ADR-100：中转的协议与端到端加密

- 日期：2026-11-16
- 状态：**提议，待维护者确认**（已答复，见文末“待维护者决定的问题”）
- 工作包：P0-05 第 2 项（设计里“中转按域名透传 TLS”的建议，以及待核实的“经透传的 TLS 怎么拿到受信任的证书”）
- 相关：ADR-099（密钥）、ADR-101（中转进来的请求只进对外面）

## 背景

中转解决“机器在路由器后面，别人连不进来”。维护者定了三件事：只转发不保存；内容端到端加密，中转读不懂；目标不在线时直接回答“对方不在线”。设计建议的做法是“中转按域名透传 TLS”：每个连上来的 Daisy 得到一个子域名，调用方对这个域名发起标准 TLS，中转只看握手里的 SNI 决定递给谁，不终止 TLS，密钥只在 Daisy 手里。好处是第三方 A2A 客户端经中转调用时只需要普通的 HTTPS。

待核实的是：Daisy 怎么为这个子域名拿到受信任的证书、签发方的频率限制、拿不到时的退路。另外还要定 Daisy 到中转的长连接用什么。

## 核实结果（2026-11-16，查官方文档）

### 证书签发的三种质询

出处：Let's Encrypt《Challenge Types》、RFC 8737。

| 质询 | 端口 | 能否签通配 | 经 SNI 透传是否可行 |
| --- | --- | --- | --- |
| **TLS-ALPN-01** | 只走 443 | 不能 | **可行，而且中转不用写任何专门代码。** 签发方向 `<子域名>:443` 发起 TLS 握手，SNI 是这个子域名，ALPN 是 `acme-tls/1`。中转按 SNI 照常透传给 Daisy，Daisy 在自己的 TLS 服务端里看到 ALPN 是 `acme-tls/1` 时，返回带质询扩展的自签名证书。条件：中转必须在公网 443 上监听；对这个 SNI 不能终止 TLS。Let's Encrypt 文档原话说这种质询最适合“TLS 终止型反向代理的作者”，客户端支持较少。Node 侧：`acme-client` 5.3.0 起有 `createAlpnCertificate`；按其仓库的一条说明，Node 20.18 / 22.9 起可以在 Node 里直接按 ALPN 选证书，不需要前置 nginx |
| HTTP-01 | 只走 80 | 不能 | 可行，但要中转做事：中转在 80 上收明文 HTTP，按 `Host` 头把 `/.well-known/acme-challenge/…` 沿隧道转给对应的 Daisy。质询内容本来就是公开的，不泄密。缺点是中转要多一个明文 HTTP 的路由，有的网络封 80 |
| DNS-01 | 无 | 能 | 只有管 DNS 的一方能做，也就是中转运营者。若由中转申请 `*.relay.example` 的通配证书，私钥在中转手里，中转就能解密，**违反端到端加密的要求，排除**。若中转为每个 Daisy 代写 `_acme-challenge.<子域名>` 的 TXT（Daisy 自己持钥申请），可行，但中转要持有 DNS 服务商的 API 凭据，比 TLS-ALPN-01 复杂得多 |

另外：Let's Encrypt 只签 RSA 和 ECDSA 密钥的证书，不签 Ed25519（常识，未在本次逐条核实）。所以 Daisy 的 TLS 密钥是一把单独的 ECDSA P-256，和身份密钥（Ed25519，ADR-099）分开。

### Let's Encrypt 当前的频率限制

出处：Let's Encrypt《Rate Limits》，2026-11-16 读取。

| 限制 | 额度 | 回补 | 能否申请放宽 |
| --- | --- | --- | --- |
| 每个注册域名的新证书 | 7 天 50 张 | 每 202 分钟 1 张 | 能，填表，要几周 |
| 每个账户的新订单 | 3 小时 300 个 | 每 36 秒 1 个 | 能 |
| 完全相同的一组域名的重复证书 | 7 天 5 张 | 每 34 小时 1 张 | 不能 |
| 每个账户每个域名的验证失败 | 每小时 5 次 | 每 12 分钟 1 次 | 不能 |
| 每个 IP 的新账户注册 | 3 小时 10 个 | 每 18 分钟 1 个 | 不能 |

- **注册域名按公共后缀列表（PSL）算**。`<id>.relay.example.com` 的注册域名是 `example.com`，所以**一个中转下所有 Daisy 共用每周 50 张新证书的额度**（还要和这个域名下其他用途的证书共用）。
- **续期不占这个额度**：按 ARI 续期的订单免除全部限制；不走 ARI、但域名组完全相同的续期，免除“新订单”和“注册域名”两项，仍受“重复证书”和“验证失败”限制。
- 放宽额度的申请面向大型托管商和集成方，处理要几周，不能应急。

**对“每个 Daisy 一个子域名”的影响**：

- 团队自己架的中转（几十个 Daisy）：每周 50 张新证书足够，续期不占额度，没有问题。注意同一个出口 IP 后面的 Daisy 第一次注册 ACME 账户受“3 小时 10 个”限制，同一办公室一次装三十台时要排队（每 18 分钟补 1 个），客户端要按退避重试。
- 公开中转、每周新增超过 50 个 Daisy：要么申请放宽，要么让中转的域名进 PSL。

### 能不能用通配证书或 PSL 绕过

- **通配证书**：只能用 DNS-01，只能由中转运营者申请，私钥在中转手里，违反端到端加密。不可用。
- **PSL**：PSL 的指南明确写着“不接受唯一目的是绕过第三方频率限制的条目”（点名 Let's Encrypt），并指向 Let's Encrypt 的放宽申请表。但**公开中转有正当的进 PSL 的理由**：各子域名属于不同的主人，主人的网页（阶段 5 手机经中转打开本地网页，P5-03）会在这些子域名下设 Cookie，进 PSL 后浏览器把它们当作互不相干的站点，防止一个子域名给别人设 Cookie。进了 PSL，频率限制按子域名分别计算是附带效果。PSL 的要求：私有段条目要有 `_psl` TXT 记录指向申请；域名有效期要超过提交日两年以上；没有处理时限承诺。团队自架的中转不需要。
- 无论进不进 PSL，Daisy 的网页 Cookie 一律用 `__Host-` 前缀（不带 `Domain`、必须 `Secure`、路径为 `/`），这样别的子域名设的 Cookie 盖不住它。

### 一个必须写明的限度：中转运营者总能拿到你子域名的证书

中转运营者控制着这个域名的 DNS 和 443 端口，它随时可以自己去签一张 `<你的子域名>` 的受信任证书，然后在中间解密。**所以单靠 WebPKI 证书，挡得住被动窃听和第三方，挡不住一个存心作恶的中转运营者。** 设计里说“中转可以由任何人运营”，前提是有额外的一层：

- **Daisy 与 Daisy 之间**：调用方从身份名片里已经有被调用方的身份公钥（ADR-099）。被调用方用身份私钥签一份“TLS 绑定声明”（内容：当前 TLS 公钥的 SPKI SHA-256、有效期），放在固定路径下。调用方建立 TLS 之后、**发出任何令牌之前**，先取这份声明，用通讯录里的公钥验签，再比对这条连接上对方证书的 SPKI。对不上就断开并告警。中转自签的证书产不出这份声明，因为它没有身份私钥。这一层对自签名证书同样有效（见下文退路）。
- **第三方 A2A 客户端**：只有 WebPKI。补救是 Daisy 监看证书透明度日志（CT），发现有不是自己申请的、针对自己子域名的证书时告诉主人。作为可选功能，阶段 5 之后做。
- 文档里如实写：用别人运营的中转时，Daisy 之间的调用不怕中转作恶；第三方客户端经中转调用，要信任中转运营者不去冒签证书。

### 拿不到证书时的退路

Daisy 用自签名证书（同样是那把 ECDSA P-256 密钥），靠上面的 TLS 绑定声明认证：

- Daisy 之间的调用：完全可用，安全性与 CA 证书相同甚至更好（不依赖 CA）。
- 第三方 A2A 客户端、手机浏览器：会报证书不受信任，**经中转用不了**。在 `daisy status`、设置页、文档里写明，名片里也只把中转地址给 Daisy 之间用。

### 目标不在线时怎么回答（透传带来的新问题）

设计要求目标不在线时“直接回答对方不在线”。但透传模式下，中转对某个子域名没有证书，**没法在 TLS 里面回一个 HTTP 响应**，只能在握手阶段拒绝。可选做法见下文方案 D。

## 可选方案

### A. 端到端加密的做法

| 方案 | 后果 |
| --- | --- |
| **A1. 按 SNI 透传 TLS，Daisy 用 TLS-ALPN-01 自己申请证书**（设计的建议） | 标准 TLS，第三方客户端零改动；中转只看到 SNI 和密文（满足“中转上看不到任何明文”）；中转实现最简单（只按 SNI 转发，不终止 TLS，ACME 质询自然透传）。约束：中转要占公网 443；受频率限制（见上）；对作恶的中转需要 TLS 绑定声明补一层 |
| A2. 透传 TLS，Daisy 用 HTTP-01 申请 | 同 A1，但中转还要在 80 上做明文 HTTP 路由；80 被封的网络里签不了。可以作为 A1 失败时的第二选择 |
| A3. 中转终止 TLS（持有通配证书），里面再套一层应用层加密 | 中转能看到 HTTP 头、路径、令牌；内层加密是自己发明的，第三方客户端不认识。违背“中转读不懂内容”和“标准优先”，排除 |
| A4. 不用 TLS，Daisy 之间用自定的端到端加密信封（比如用身份密钥做 HPKE） | 第三方客户端完全不能经中转调用；是自定协议。排除 |

### B. Daisy 用什么证书

| 方案 | 后果 |
| --- | --- |
| **B1. 默认向 Let's Encrypt 申请（TLS-ALPN-01），每个 Daisy 自己一个 ACME 账户，TLS 密钥续期时复用；申请不到时退到自签名 + 绑定声明** | 第三方能用；中转永远拿不到私钥；退路明确。续期按 ARI 走时不占额度 |
| B2. ACME 目录地址可配置（比如 ZeroSSL、Google Trust Services 等其他支持 ACME 的 CA） | 分散频率限制。各家的额度、是否要外部账户绑定（EAB）、是否支持 TLS-ALPN-01，**本次未核实**。建议做成配置项，默认 Let's Encrypt |
| B3. 永远只用自签名 + 绑定声明 | 最简单、不受任何 CA 限制，但第三方客户端经中转一律用不了，不满足阶段 5 的完成标准（“被另一个网络里的智能体调用成功”，若那个智能体是第三方） |

### C. Daisy 到中转的长连接

透传模式下，中转递给 Daisy 的是一条条原始的 TCP 字节流（每条是一个外来的 TLS 连接），不是 HTTP 请求。所以隧道要能承载“多条双向字节流”。

| 方案 | 后果 |
| --- | --- |
| **C1. 一条控制 WebSocket + 每个外来连接反连一条数据 WebSocket**：Daisy 连到中转自己的域名（`wss://relay.example/…`，中转终止这一层 TLS），用身份密钥签中转给的挑战来登记；有外来连接时，中转在控制通道上发“有新连接 #n”，Daisy 新开一条数据 WebSocket 认领 #n，中转把两边的字节对接 | 实现最简单：现有依赖里就有 `ws`；不需要自己做多路复用和流控（每条外来连接有自己的 TCP 流控）；只走 443，能穿过大多数企业防火墙和 HTTP 代理。代价：每个外来连接多一个往返（A2A 调用本来就是秒级，影响很小）；外来连接多时 WebSocket 也多 |
| C2. 一条 WebSocket 上做多路复用（yamux 规范，或自定分帧） | 一个连接、没有额外往返。yamux 有现成规范，但 JS 实现绑在 libp2p 的接口上，较重；自定分帧要自己做流控和队头阻塞处理，等于发明协议 |
| C3. HTTP/2：Daisy 开一条到中转的 HTTP/2 连接，中转通知后，Daisy 在同一连接上用扩展 CONNECT（RFC 8441）开流 | 标准协议、内置流控，Node 的 `http2` 原生支持。但中转和 Daisy 两边对扩展 CONNECT 的处理要细抠；经 HTTP 代理时比 WebSocket 少见 |
| C4. SSH 反向端口转发（RFC 4254 的 `tcpip-forward`） | 完全标准，还能直接用 Ed25519 身份密钥认证。但通常走 22 端口，企业网常封；和 443 上的 TLS 透传共用端口做不到（SSH 没有 SNI）；要引入 SSH 库 |
| C5. QUIC / WebTransport | Node 的 QUIC 仍是实验性的，排除 |

无论选哪种，Daisy 与中转之间的这层控制协议是新写的（不存在一个“反向隧道”的通行标准）。它不碰内容，内容仍是标准 TLS；要把它写成一份带版本号的短规范，和中转一起发布，供别人自己实现中转。

### D. 目标不在线时的回答

| 方案 | 后果 |
| --- | --- |
| **D1. 握手阶段拒绝（TLS 警报 `unrecognized_name`），另给一个中转自己的查询接口**：`https://relay.example/v1/presence/<子域名>` 回答在不在线。Daisy 作为调用方先查它（或握手失败后查它），给出“对方不在线” | 中转永远看不到发给离线 Daisy 的请求内容和令牌。第三方客户端看到的是一个连接错误，不是一条清楚的“不在线”消息，文档里写明 |
| D2. 中转持有一张通配证书，**只在目标不在线时**用它终止 TLS，回一个 HTTP 503 加 A2A 格式的“对方不在线”错误 | 所有客户端都得到一条清楚的回答。但第三方客户端会在这条 TLS 里把请求连同 Bearer 令牌一起发给中转：中转能读到发给离线 Daisy 的内容，并可能在令牌有效期内（几分钟）等对方上线后重放。这削弱了“中转读不懂内容”。Daisy 自己的客户端会先校验绑定声明，不会把令牌交出去 |

## 推荐

1. **加密：A1。** 中转按 SNI 透传 TLS，不终止。中转自己的域名（`relay.example`）由中转终止 TLS，只用于控制连接、数据连接和在线查询；其余 `*.relay.example` 的 SNI 一律透传。
2. **证书：B1 + B2。** 每个 Daisy 自己一个 ACME 账户和一把 ECDSA P-256 TLS 密钥（续期复用，便于固定），默认 Let's Encrypt，用 TLS-ALPN-01；ACME 目录可配置；HTTP-01 作为中转可选支持的第二选择。拿不到证书时退到自签名，`daisy status` 写明“经中转只有 Daisy 之间能用”。
3. **子域名从身份编号派生**：取身份公钥指纹的前 160 位，小写 base32（32 个字符）。中转只把这个子域名分给能用对应私钥签挑战的那个 Daisy。这样子域名稳定，换中转连接、重启都不变，证书一直有效；也省掉“名字先到先得”的抢注问题。好记的别名以后再说。
4. **TLS 绑定声明**：Daisy 之间经中转（以及直连时）的调用，在发令牌之前先校验对方用身份私钥签过的 TLS 公钥声明。这一条写进 P0-04 的 A2A 用法契约，作为 Daisy 客户端的行为，不是对第三方的要求。
5. **长连接：C1**（控制 WebSocket + 每个外来连接反连一条数据 WebSocket），协议带版本号，写成短规范随中转发布。以后外来连接多、往返明显时，在新版本里换成 C2 或 C3，不影响端到端那一层。
6. **不在线：D1**（握手拒绝 + 在线查询接口），因为它不让中转碰到任何请求内容和令牌。D2 能给第三方更友好的回答，但代价落在“安全与主人主权”这条首要原则上，请维护者决定。
7. **公开中转**的运营者应把域名申请进 PSL（理由是 Cookie 隔离，不是频率限制）；团队自架的中转不需要。Cookie 一律 `__Host-` 前缀。
8. 文档里如实写明“作恶的中转运营者能对第三方客户端冒签证书”这一限度，以及 CT 监看作为以后的可选功能。

## 对工作包的影响

- **P0-04 契约**：A2A 用法里加“TLS 绑定声明”的路径、字段、校验顺序；身份名片里加中转地址（子域名）。
- **P5-01 中转程序**：只做 SNI 路由、控制/数据 WebSocket、在线查询、速率与并发上限；不需要任何 ACME 代码（TLS-ALPN-01 自然透传）；若支持 HTTP-01，要在 80 上做按 `Host` 的明文转发。抓包验证：中转上只能看到 SNI 和 TLS 密文。
- **P5-02 Daisy 的中转连接**：ACME 客户端（`acme-client`）、证书续期（优先 ARI）、证书与密钥存放在数据目录（ADR-099、ADR-102）；把中转递来的字节流注入对外面的 TLS 服务端（ADR-101）；退路与 `daisy status` 的说明。
- **P5-03 配对与手机**：手机浏览器经中转打开网页依赖受信任证书；退到自签名时手机经中转用不了，要写明。
- **验收**：“中转上看不到明文”之外再加一条“中转作恶模拟”：中转换上自己签的证书，Daisy 调用方必须拒绝并告警。
- **部署**：架中转的机器要能占用公网 443（以及可选的 80），域名要能设 `*.relay.example` 的通配 DNS 记录指向中转。

## 待维护者决定的问题（已答复：1、2、3、5 按推荐；中转先用假域名和本地证书机构开发测试）

1. **同意“按 SNI 透传 + Daisy 用 TLS-ALPN-01 自己申请证书”作为中转的加密做法吗？** 推荐同意。替代方案（中转终止 TLS）违背“中转读不懂内容”。
2. **目标不在线时：D1 还是 D2？** D1：中转碰不到任何内容，但第三方客户端只看到连接错误。D2：所有客户端都收到清楚的“对方不在线”，但第三方客户端发往离线 Daisy 的请求和令牌会被中转看到。推荐 D1。
3. **是否接受“作恶的中转运营者可以对第三方客户端冒签证书”这一限度**，并写进文档？Daisy 之间的调用靠 TLS 绑定声明不受影响。推荐接受，CT 监看列为以后的可选功能。
4. **团队的中转用什么域名、由谁架、能不能占 443？** 这决定频率限制是否够用（每周 50 张新证书，团队规模足够），也决定阶段 5 的验收环境。默认是“只提供可自架的程序，团队自己架一个”。
5. **长连接用 C1（每个外来连接反连一条 WebSocket）可以吗？** 推荐 C1，简单、穿透性好；性能不够时再换多路复用。
