# ADR-104：更新与重启时怎么对待正在运行的会话

- 日期：2026-11-16
- 状态：**部分确认**（2026-11-17）：自动更新在 P1-04 的备份与退回落地之前默认关、之后团队内部默认开（维护者的决定）；其余按推荐作为施工默认值
- 工作包：P0-05 第 6 项（P1-02 的“更新与重启”；设计建议“更新要等空闲”）
- 相关：P1-02、P1-04、P1-07（`daisy update`）、P5-06；沿用旧版的约定（结构只增不删；旁建、原子切换、守卫回退；后台任务不无限挡住重启）

## 背景

合成一个进程之后，Daisy 重启，它拉起的 harness 进程也跟着结束，正在执行的那一轮就被打断；被打断的不重放（“不重放副作用”原则）。所以 P1-02 已经定了方向：更新等空闲；主人强制更新时，告诉他会打断哪些会话。这条记录把“什么算空闲”“怎么等”“强制时怎么告知”“数据库怎么备份和退回”“代码怎么切换和回退”写实。

现有可以沿用的东西：

- `packages/daisy/src/update/autoupdate.ts`（旧版的自动更新）：新版本在旁边建好，空闲 60 秒后原子切换 `current`，退出码 75 让服务管理器拉起；新版本 120 秒内不健康，守卫把 `current` 指回上一版。
- `packages/daisy/src/update/restart-drain.ts`（旧版的重启排空）：等重启时，后台命令、监视器最多再等 30 分钟（只计“除了后台任务都空闲”的时间），之后停掉并如实回报。
- `packages/daisy/src/store/index.ts`（旧版的结构迁移）：结构变更按 `PRAGMA user_version` 有序、只增不删，旧代码能在新结构上跑。
- `packages/daisy/src/update/lifecycle.ts`、`leadership.ts`：控制面不间断发布（待命进程、租约交接）。单主人单进程之后不再需要，但“排空再退出”的思路要用。

## 可选方案

### A. 运行中的 harness 进程在重启时怎么办

| 方案 | 后果 |
| --- | --- |
| **A1. 等空闲再重启；强制时打断并标为中断** | 符合“不重放副作用”和 P1-02。代价：一直有会话在跑的 Daisy，更新可能等很久 |
| A2. 让 harness 进程跨重启存活，新进程重新接上 | 不打断任何一轮。但 Claude Code 的流式 JSON、Codex 的 App Server、ACP 都走子进程的标准输入输出，父进程一退出管道就断了，要接回来只能在中间放一个常驻的“持管道”进程，等于又回到两个进程，违背“合成一个程序”和“一个进程”的原则 |
| A3. 不等，重启时把被打断的轮次自动续上 | 违背“不重放副作用”（可能重复工具副作用）。排除 |

### B. 什么算“空闲”，等多久

| 方案 | 后果 |
| --- | --- |
| B1. 只看“有没有一轮在执行” | 简单，但会打断正在登录 harness、正在用终端、正在等卡片回答的会话 |
| **B2. 一张明确的“忙”清单，按类别给等待上限**（见推荐） | 每类都有可预期的行为；自动更新永远不打断“一轮”；后台类的工作有上限，不会无限期挡住更新 |

### C. 数据库备份与退回

| 方案 | 后果 |
| --- | --- |
| **C1. 只在结构版本要升时备份：迁移前用 SQLite 的 `VACUUM INTO` 写一份一致的副本到 `backups/`；迁移在一个事务里做；结构变更沿用旧版的“只增不删”** | 不改结构的更新不产生备份，磁盘占用小；`VACUUM INTO` 在 WAL 模式下也能拿到一致快照，不用停服务。旧代码能在新结构上跑，所以代码回退通常不需要恢复数据库 |
| C2. 每次更新都整库备份 | 简单、可预期，但数据库大时（长会话的事件流可以到几百 MB）每次更新都要拷一遍 |
| C3. 不备份，只靠迁移在事务里做 | 迁移失败能回滚，但“迁移成功、新版本有问题、要回到旧结构”的情况没有退路，不满足“升级失败时能退回” |

### D. 代码怎么切换、怎么回退

| 方案 | 后果 |
| --- | --- |
| **D1. 沿用旧版的自动更新做法：新版本在数据目录的 `versions/<版本>/` 旁边建好（不影响运行），等到空闲后原子切换“当前版本”指针，退出，由服务管理器或 Daisy 自己拉起新版本；新版本在确认期内不健康，就指回上一版** | 已有实现和测试，换的只是“更新谁”（整个 Daisy 而不是 Runner）和“代码从哪来”。和安装方式解耦：包管理器只负责第一次装 |
| D2. 直接用包管理器原地升级（`npm i -g …@新版本`），然后重启 | 最省事。但升级会在进程运行时替换它的文件，进程后来再按需加载的模块会是新旧混搭；回退要靠再装一次旧版本，不原子。若要选它，必须把 Daisy 打成单个 JS 文件（启动时一次加载完），并另做回退 |

## 推荐

**A1 + B2 + C1 + D1。**

### 1. 什么算忙（B2）

| 类别 | 算忙吗 | 等待上限 | 到了上限之后 |
| --- | --- | --- | --- |
| 一轮正在执行（含只问支线、常驻 agent 的来访对话、正在执行的 A2A 任务） | 忙 | 自动更新：**无上限**，永不打断 | — |
| 一轮在等卡片（工具授权、AI 提问） | 忙（harness 进程在等，重启会打断） | 自动更新：无上限 | 等待超过 24 小时，给主人一条通知：“有更新在等，被这几个会话挡着”，由主人决定 |
| 登录 harness 的任务、终端窗口、本机命令 | 忙 | 无上限 | 同上，通知主人 |
| 后台命令、监视器、harness 自己的后台任务 | 忙 | 沿用旧版的约定：30 分钟（只计其余都空闲的时间） | 停掉并如实回报给会话（`lost`），然后继续走重启 |
| 定时唤醒、周期任务（还没到点） | 不算 | — | 它们存在数据库里，重启后照常触发；到点时 Daisy 恰好在重启，就在启动后补触发一次 |
| 只是排队、还没开始的输入 | 不算 | — | 输入已经持久化，重启后照常开始 |

### 2. 怎么等、怎么退出

1. 发现新版本 → 在旁边建好（不打断任何事）→ 状态“有更新，空闲时重启”，`daisy status` 和设置页显示，并列出正在挡着的会话。
2. 进入空闲后，再连续空闲 60 秒（沿用现值）→ 进入**排空**：新来的输入、新的 A2A 消息照常接收并持久化，但不开始执行（A2A 的阻塞调用连接会在重启时断开，调用方照 A2A 的幂等约定用同一个 messageId 重发，拿到的是同一个任务）；不再开始新的一轮。
3. 排空期间如果有东西开始执行（比如一个定时唤醒刚好到点），取消这次重启，回到第 1 步。
4. 关两个面、写备份（如果要迁移）、回收所有子进程（不留任何会话的进程）、释放数据目录锁、退出。
5. 拉起新版本：有服务管理器（systemd 用户单元、macOS LaunchAgent）时退出码 75 交给它；没有服务管理器时（比如 Windows 上手动 `daisy start`），Daisy 先以分离方式启动新进程再退出，新进程等到拿到数据目录锁再继续。注意 systemd 的 `KillMode=control-group` 会杀掉单元里残留的进程，所以有服务管理器时不能用“先起新的再退出”。

### 3. 强制更新

- 入口：`daisy update --now`，以及设置页上的“立即更新”。
- 先列出会被打断的东西：每个会话的名字、状态（执行中 / 等卡片 / 登录中 / 终端）、已经运行了多久；正在执行的外来 A2A 任务列出调用方。命令行要 `--yes` 才执行，网页要点确认。
- 执行后：被打断的轮次标为“中断”，会话里留一条“被 Daisy 更新打断，没有重放；需要的话请再发一次”（与进程被强行结束后重启时的行为一致）；等卡片的卡片作废；外来的 A2A 任务回 `failed`，说明“被对方 Daisy 更新打断，未重放”，调用方可以用新的 messageId 重发。
- 强制更新不要 PIN（权限设计把更新列在“系统”类，不要 PIN），但审计里记一条，写明是谁、经哪个入口、打断了哪些会话。
- 主人的普通重启（`daisy stop`、`daisy start`）用同一套“先列出会打断什么”的逻辑；`daisy stop` 默认等空闲，`--now` 才打断。

### 4. 数据库备份与退回（C1）

- 只要新版本的结构版本高于数据库里的，迁移前先 `VACUUM INTO backups/daisy-<旧版本>-schema<旧结构版本>-<时间>.sqlite`，文件 0600；备份写成功后才迁移；迁移在一个事务里，失败就整体回滚、不切换代码、记录原因。
- 默认保留最近 3 份，可以配置。
- 结构变更继续遵守旧版的约定：只加表、加带默认值的列、加索引；不删、不改名。这样代码回退到上一版时，上一版能在新结构上照常跑，**不需要恢复数据库**。
- 确实需要一次不兼容的结构变更时（只应出现在主版本），这个版本声明“不可自动回退”。它的确认期内若不健康，守卫恢复迁移前的备份再指回旧版本——这时新版本从没成功跑起来，恢复不会丢数据。确认期过后要退回，必须由主人明确执行（`daisy update --rollback`），并先告诉他“会丢掉自 <时间> 以来的数据”。
- `node:sqlite` 的在线备份接口也可以用（较新的 Node 版本提供，本次未核实具体版本），`VACUUM INTO` 是 SQLite 自身的功能，不依赖 Node 版本，作为默认。

### 5. 代码切换与回退（D1）

- 版本目录在数据目录的 `versions/<版本>/`，只读；“当前版本”和“上一版”是两个指针（Linux、macOS 用软链；Windows 上软链要特权，改用一个小的指针文件，由启动器读取）。
- 新版本的确认：启动后 120 秒内（沿用现值）完成迁移、两个面都在监听、数据库可读写，写一条“已确认”；否则守卫回退。
- 代码从哪来：阶段 1 内部使用时沿用旧版自动更新的信任根（GitHub 上指定仓库的 main，只向前）；阶段 5 起改成发布到 npm 的版本（校验包的完整性和来源证明）。具体安装形态由 P5-06 定（当时待定），这里只定“旁建、切换、回退”这套结构。
- 自动更新可以关掉（设置项），关掉后 `daisy update` 手动更新仍走同样的等空闲流程。

## 对工作包的影响

- **P1-02**：合并时把 `restart-drain.ts`、`autoupdate.ts`、`upgrade.ts`、`restart.ts` 的逻辑从“更新 Runner”改成“更新整个 Daisy”，忙的判定用上面的清单；删掉 `leadership.ts`、`lifecycle.ts` 的租约交接，保留“排空”。
- **P1-04**：`VACUUM INTO` 备份、保留份数、迁移事务、“不可自动回退”标记；升级测试覆盖：升级前有备份、迁移失败不切换、确认期内失败自动回退、确认期后手动回退会提示丢数据。
- **P1-07**：`daisy update`（`--now`、`--yes`、`--rollback`）、`daisy stop --now`、`daisy status` 显示“有更新在等，被谁挡着”。
- **P1-08**：设置页的更新区块。
- **P1-09**：systemd 用户单元用 `Restart=on-failure` 并把退出码 75 当作“立即重启”（`RestartForceExitStatus=75`）。
- **P4-04**：排空期间收到的 A2A 消息照常落库；强制更新时外来任务回 `failed`。
- **P5-04、P5-05、P5-06**：macOS LaunchAgent、Windows 的拉起方式（无服务管理器时分离启动）、版本指针文件；三个系统上的升级与退回测试。

## 待维护者决定的问题（已答复：自动更新在备份与退回落地之前默认关；其余按推荐）

1. **等卡片的会话算不算忙？** 推荐算忙：harness 进程正在等回答，重启会打断这一轮。代价是一张没人理的卡片会挡住自动更新（最长到卡片七天过期），所以超过 24 小时会通知你自己决定。另一个选择是“等卡片超过 N 小时就允许自动更新打断它”，代价是主人回来时那一轮已经没了。
2. **强制更新要不要 PIN？** 推荐不要（权限设计把更新列在不要 PIN 的“系统”类），但要确认并记审计。要的话，AI 就不能经命令行强制更新、打断主人的会话。
3. **数据库备份默认保留几份？** 推荐 3 份，只在结构版本升级时备份。
4. **自动更新默认开还是关？** 推荐阶段 1 团队内部默认开（与现在 Runner 的行为一致）；阶段 6 开源时再定对外的默认值。
