# ADR-099：密钥与加密——算法、库、密钥存放与权限

- 日期：2026-11-16
- 状态：**部分确认**（2026-11-17）：PIN 最短 6 位、可以是纯数字（维护者的决定，不同于本文推荐的“6 位允许字母数字”的更严版本；风险作为已知限制写明）；其余各问按推荐作为施工默认值，阶段关口再确认
- 工作包：P0-05 第 1 项
- 相关：契约 P0-04；ADR-100（中转证书）、ADR-102（数据目录）

## 背景

Daisy 去中心之后，每个 Daisy 自己就是签发方。设计的安全基线要求“签名与加密用成熟的公开算法和现成的库，不自己实现”“凭据文件只有主人可读”“只保存 PIN 的校验值”，并把“具体的加密方案”留到阶段 0。和契约（P0-04）那边对齐的起点提议是：

- 签名：Ed25519；令牌格式 JWS / JWT，算法 EdDSA；
- 库：Node 内置 `node:crypto`；
- 身份编号 = 公钥的 SHA-256 指纹；
- PIN：scrypt；
- 私钥：数据目录里的 0600 文件。

这条记录把这个起点逐项落实，补上它没覆盖的几处，并回答“要不要用系统钥匙串”。

### 一个 Daisy 要保管的秘密（盘点）

| 秘密 | 用途 | 生命周期 | 现状 |
| --- | --- | --- | --- |
| 身份签名密钥（私钥） | 给发往别的 Daisy 的令牌签名；给身份名片和 TLS 绑定声明签名（ADR-100） | 长期，首次启动生成 | 新增 |
| 本机凭据 | 命令行访问本机面（P1-03） | 长期，可轮换 | 新增（类似现有 `ACCESS.md`） |
| 网页会话与一次性口令 | 本地网页登录（`daisy open`） | 短期 | 部分已有 |
| AI 工作凭据 | 每一轮一张，只能用 AI 自用的工具 | 一轮 | 已有形态，要改 |
| 设备凭据 | 配对过的设备（P5-03） | 长期，可单独吊销 | 新增 |
| PIN 校验值 | 放别人进来 | 长期 | 新增 |
| 身份档里的 API key | harness 调模型 | 长期 | 已有：`master.key` + AES-256-GCM（`store.ts`） |
| 中转用的 TLS 私钥、ACME 账户私钥 | 经中转对外的 TLS（ADR-100） | 长期，证书定期续 | 新增，阶段 5 |

### 必须先说清楚的一个事实：同一个系统账户里没有秘密

AI 以主人的系统账户运行。凡是 Daisy 进程读得到的东西，AI 用 shell 工具都读得到：数据目录里的私钥、PIN 校验值、数据库文件本身。它还能直接改数据库、改 Daisy 自己的代码。所以：

- 文件权限（0600 或 Windows 上的 ACL）挡的是**同一台机器上的其他系统账户**（团队服务器上的其他人），挡不住主人自己的 AI。
- 系统钥匙串在这一点上也一样：macOS 的钥匙串、Windows 的 DPAPI、Linux 的 Secret Service 都以“登录用户”为边界，同一用户的进程基本都能取到（下文详述）。
- **PIN 挡的是“走接口”这条路**：AI 不知道 PIN，就不能经命令行或接口做“放别人进来”的操作。但 PIN 挡不住一个存心绕过的 AI 直接改库（比如往通讯录表里插一行），也挡不住它拿 PIN 校验值离线穷举短 PIN。设计文档的已知限制原先写的是“PIN 保护的那一类不受影响，因为 AI 不知道 PIN”，这句话**说得过满**，建议改成如实的说法（见文末问题 4）。要真正隔开，只能让 AI 在另一个系统账户里运行，这已列为“不在这一次”。

这不是这条记录能解决的问题，但它决定了下面几个选择“值不值得”：凡是只防同账户进程的加固，收益都很小。

## 可选方案

### A. 签名算法与令牌格式

| 方案 | 后果 |
| --- | --- |
| **A1. Ed25519 + JWS（紧凑序列化）/ JWT** | 密钥 32 字节、签名 64 字节、确定性签名（不依赖随机数质量）；`node:crypto` 原生支持生成、签名、验证、导出 JWK；JWT 是 OAuth2 生态的标准格式（设计要求“令牌用 OAuth2 的签名令牌格式”），外部签发方、MCP 授权都说这个格式。缺点：Let's Encrypt 不签 Ed25519 证书，所以中转用的 TLS 密钥必须另用 ECDSA P-256（见 ADR-100），身份密钥和 TLS 密钥是两把 |
| A2. ECDSA P-256（ES256）+ JWT | 兼容面最广（浏览器 WebCrypto、所有 JWT 库、Let's Encrypt 都支持），身份密钥可以直接当 TLS 密钥。缺点：签名需要好的随机数（实现不当会泄露私钥，好在由库处理）；密钥和签名都更长；和契约那边的起点不一致 |
| A3. 不透明随机令牌 + 查表验证（不签名） | 实现最简单、可即时吊销。但跨 Daisy 的令牌必须能离线验证（被调用方没有调用方的数据库），所以只能用于本机内部的凭据，不能单独构成方案 |

**算法标识的一个新情况**：RFC 9864（2025-10，Fully-Specified Algorithms for JOSE and COSE）把多义的 `EdDSA` 标为弃用，新增了明确到曲线的 `Ed25519`。截至今天主流库的支持程度不一（未逐个核实）。所以契约里要写清：签发时用哪个标识，验证时认哪几个。

### B. 库

| 方案 | 后果 |
| --- | --- |
| B1. 只用 `node:crypto`，JWS/JWT 的编码、解析、校验自己写 | 零依赖。但 JWT 的漏洞历来出在“解析与校验”这一层（`alg: none`、算法混淆、`kid` 注入、`exp`/`nbf`/`aud` 漏检），这正是安全基线说的“不自己实现”要防的地方。阶段 2 的外部签发方（P2-01）还要取对方的 JWKS、缓存、轮换、验证它选的算法（可能是 RS256、ES256），自己写的面会越来越大 |
| **B2. `node:crypto` 做底层原语，JOSE 层用 `jose`（panva/jose）** | `jose` 无依赖、维护活跃、被大量 OAuth/OIDC 项目使用，覆盖 JWS/JWT/JWK/JWKS、JWK 指纹（RFC 7638）和远程 JWKS 缓存。多一个依赖，要锁版本、跟安全公告 |
| B3. 用 `jsonwebtoken` 等老库 | 对 EdDSA、JWKS 的支持不如 `jose`，需要再拼几个包，不推荐 |

另外两处 `node:crypto` 不够用的地方，单独说明：

- **X.509 证书与 ACME**（只在阶段 5 的中转连接里用）：`node:crypto` 只能解析证书，不能生成证书和 CSR。按 ADR-100，用 `acme-client`（5.3.0 起支持 TLS-ALPN-01，有 `createAlpnCertificate`），只在中转连接模块里引入。
- **PIN、对称加密、随机数**：`node:crypto` 的 `scrypt`、`aes-256-gcm`、`randomBytes` 足够，不另引库。

### C. 身份编号（公钥指纹）的算法

| 方案 | 后果 |
| --- | --- |
| **C1. JWK 指纹（RFC 7638，SHA-256）** | 标准算法，`jose` 现成提供；ACME、OAuth DPoP 都用它；可以直接当 JWS 头里的 `kid`。输入是规范化的 JWK（`{"crv":"Ed25519","kty":"OKP","x":"…"}`），跨语言实现一致 |
| C2. 对 SPKI DER 字节取 SHA-256 | 也常见（TLS 公钥钉用的就是它），但要约定编码细节，别的语言实现时容易差一个字节 |
| C3. 自定格式（比如截短的 base32） | 好念好抄，但是自定的 |

显示给人看时，可以在 C1 的结果上做一个**展示形式**（比如 base32 分组、只显示前 16 位做核对），但编号本身是完整的 SHA-256 指纹。

### D. PIN 的校验值

| 方案 | 后果 |
| --- | --- |
| **D1. scrypt（`node:crypto`），参数 N=2^17、r=8、p=1（约 128 MiB，单次约 0.2–0.5 秒），每个 PIN 一个 16 字节随机盐，参数随校验值一起存** | 内置、无依赖、内存困难。现有 `store.ts` 的密码校验用的就是 scrypt（但用的是 Node 默认参数 N=2^14，偏弱），沿用写法、加强参数。存参数是为了以后加强时能平滑升级 |
| D2. Argon2id | 当前首选的口令哈希，但 Node 24 内置的 `crypto.argon2` 是否稳定、三个系统上是否都可用**未核实**；用第三方原生模块会给安装带来编译问题 |
| D3. PBKDF2 | 内置，但不是内存困难，同样的耗时下更容易被 GPU 穷举 |

无论选哪个：**4 到 6 位数字的 PIN，在攻击者拿到校验值之后都挡不住离线穷举**（6 位数字只有 100 万种，按 0.3 秒一次、8 核并行，约 10 小时）。真正挡住的是在线路径上的“连续输错锁定”（P1-05）。拿得到校验值的只有同账户进程（包括 AI）和拿到磁盘的人，见上面“必须先说清楚的一个事实”。所以建议 PIN 的最短长度定为 6 位，允许更长的字母数字口令，界面提示“越长越安全”。

### E. 密钥存放

| 方案 | 后果 |
| --- | --- |
| **E1. 数据目录里的文件，只有主人可读**（Linux / macOS：目录 0700、文件 0600；Windows：见下文 ACL） | 三个系统一套代码路径；无原生依赖；无人值守启动、SSH 登录的服务器、开机自启都没问题；备份和迁移只要拷数据目录。挡得住同一主机的其他账户；挡不住同账户进程（这点任何方案都一样）；磁盘被拿走时没有额外保护（靠系统的全盘加密） |
| E2. 系统钥匙串：macOS Keychain、Windows DPAPI 或凭据管理器、Linux Secret Service | 好处：磁盘或备份泄露时私钥不是明文（DPAPI、Keychain 用登录口令派生的密钥保护）；macOS 钥匙串条目可以限制哪些程序能读。坏处：① **Linux 服务器上通常没有 Secret Service**（没有图形会话、没有 D-Bus 会话总线、没有 gnome-keyring），而团队的 Daisy 多数装在共用 Linux 服务器上，必须保留 E1 作为退路，等于维护两套；② Node 没有内置绑定，要用原生模块（常用的 `keytar` 已于 2022-12 归档停更；替代品要逐个评估），三个系统、多种 CPU 架构都要有预编译包，否则安装时要编译；③ macOS：钥匙串条目的访问控制按程序签名，Daisy 跑在 `node` 上，AI 用 `node` 跑的脚本是同一个程序，挡不住；`node` 一升级，签名变了还会弹授权框；SSH 登录或开机后尚未登录时，登录钥匙串是锁着的，无人值守启动会失败；④ Windows：DPAPI 的“当前用户”范围对同一用户的任何进程都能解密，对 AI 没有额外保护 |
| E3. 私钥用 PIN 加密后存放 | 磁盘泄露时最安全。但 Daisy 每次启动都要人输 PIN 才能签名，开机自启、无人值守、更新后自动重启全部做不到，违背“终端安装、终端控制”的定位和 P1-02 的“等空闲自动重启” |

### F. Windows 上“只有主人可读”的等价做法

Node 的 `fs.chmod` 在 Windows 上只能切换“只读”属性，0600 这类权限位不生效。现有 `secret-file.ts` 按 uid 和权限位检查，在 Windows 上会全部跳过。等价做法：

- 数据目录放在 `%LOCALAPPDATA%` 下（ADR-102）。按 Windows 的默认设置，用户配置目录只授权给该用户、`SYSTEM` 和 `Administrators`（这是常规默认值，**待在干净的 Windows 10 / 11 上用 `icacls` 实测核实**，P5-05）。
- 首次创建数据目录时显式收紧：去掉继承，只授权给当前用户的 SID 和 `SYSTEM`，子对象继承：
  `icacls "<数据目录>" /inheritance:r /grant:r "*<当前用户 SID>:(OI)(CI)F" "*S-1-5-18:(OI)(CI)F"`
  （SID 用 `whoami /user` 取；`icacls` 是系统自带的。也可以经 PowerShell 的 `Set-Acl`。）
- 启动时和 `daisy doctor` 里检查：数据目录和密钥文件的 ACL 里，除当前用户、`SYSTEM`、`Administrators` 之外没有别的主体有读权限；有就拒绝启动并给出修复命令（与现有 `readSecretFile` 在 Linux 上的行为一致）。
- `Administrators` 能接管任何文件的所有权，相当于 Linux 上的 root，不把它算作“别人”。

## 推荐

1. **签名**：Ed25519（A1）。令牌用 JWS 紧凑序列化的 JWT。**验证时 `EdDSA` 和 `Ed25519` 两个标识都认；签发时先用 `EdDSA`**（兼容面更广），等私有插件、外部的任务与聊天系统那边用的库都支持 `Ed25519` 后再切。具体字段由 P0-04 契约定。
2. **库**：`node:crypto` 做原语；JOSE 层用 `jose`（B2）；ACME 和证书只在中转模块里用 `acme-client`。这是对“只用 `node:crypto`”起点的**一处偏离**：理由是安全基线的“不自己实现”恰恰落在 JWT 的解析校验上，而 P2-01 的外部签发方迟早要用到完整的 JWKS 支持。
3. **身份编号**：Ed25519 公钥的 JWK 指纹（RFC 7638，SHA-256，base64url 无填充，43 个字符），同时用作 JWS 的 `kid`。给人核对时显示分组的短形式。
4. **本机内部的凭据不签名**：本机凭据、网页会话、设备凭据都用 256 位随机串，库里只存 SHA-256 哈希，查表验证，可即时吊销。AI 工作凭据交给 harness 里的 MCP 时，按 P2-02 用 Daisy 自签的短期 JWT（≤ 1 小时）。哪些凭据走哪种，在 P0-04 契约里逐个写明。
5. **PIN**：scrypt，N=2^17、r=8、p=1，16 字节盐，参数随校验值存（这组参数要约 128 MiB，超过 `node:crypto` 默认的 32 MiB 上限，调用时要显式给 `maxmem`）；最短 6 位，允许字母数字；比较用定长时间比较。
6. **密钥存放**：E1，数据目录里的文件。目录 0700、文件 0600；Windows 用上面的 ACL 做法。启动时检查属主和权限，不对就拒绝启动并说明怎么修。私钥和 `master.key` 不进日志、不进备份以外的任何地方（数据库备份见 ADR-104，备份文件同样 0600）。
7. **系统钥匙串不作为默认，也不在这一次做**。它对团队最主要的部署（Linux 服务器）不可用，对最主要的威胁（同账户的 AI）没有帮助，却要引入原生模块和两套代码路径。如果以后要防“笔记本丢失、备份泄露”，优先建议用户开系统的全盘加密；钥匙串可以作为阶段 6 之后的可选加固，届时单独写一条记录。

## 对工作包的影响

- **P0-04 契约**：令牌的 `alg`（签发 `EdDSA`，验证两者都认）、`kid` = 身份编号、身份名片里的公钥写成 JWK；本机凭据和跨 Daisy 令牌两类分开写。
- **P1-03**：本机凭据、网页会话、AI 工作凭据按推荐第 4 条实现；凭据文件的检查在 Windows 上走 ACL 分支（阶段 1 只跑 Linux，但代码路径和测试从这一步留好）。
- **P1-04**：数据目录创建时设权限；`master.key` 沿用。
- **P1-05**：PIN 的参数、最短长度、锁定。
- **P2-01、P2-02**：外部签发方的 JWKS、代领令牌用 `jose`。
- **P4-01（互认）**：身份名片里放公钥 JWK 和身份编号；添加名片时显示短指纹供人核对。
- **P5-02**：中转用的 TLS 密钥是另一把 ECDSA P-256 密钥，与身份密钥分开（ADR-100）。
- **P5-05**：Windows ACL 的实测和 `doctor` 检查。
- **依赖**：新增 `jose`（阶段 1 起）、`acme-client`（阶段 5 起），都锁版本。

## 待维护者决定的问题（已答复：PIN 最短 6 位、可以是纯数字；其余按推荐）

1. **JOSE 层用 `jose` 库，还是坚持只用 `node:crypto` 自己写 JWS？** 推荐用 `jose`：少写容易出错的校验代码，外部签发方要用。后果是多一个依赖。
2. **签发令牌时的算法标识用 `EdDSA` 还是 `Ed25519`？** 推荐签发用 `EdDSA`、验证两者都认，以后再切。需要和接入的外部系统（私有插件、外部的任务与聊天系统）一起定，因为契约是几家共用的。
3. **PIN 的最短长度和形式**：推荐“至少 6 位，允许字母数字”。只允许 4 位数字会让离线穷举在几分钟内完成。
4. **是否同意把已知限制里的说法改得更如实**：现在写“PIN 保护的那一类不受影响，因为 AI 不知道 PIN”。推荐改成：“PIN 挡住的是 AI 经命令行和接口做这类操作；AI 和 Daisy 用同一个系统账户，一个存心绕过的 AI 仍能直接改数据库或改 Daisy 的代码，真正的隔离要把 AI 放到另一个系统账户（不在这一次）。”它改变的是安全承诺，所以要维护者确认。
5. **系统钥匙串**：同意“这一次不做，以后作为可选加固”吗？如果你希望 macOS 笔记本上默认用钥匙串，代价是多一个原生依赖和两套代码路径，且对 AI 没有额外保护。

## 关口决定

阶段 4 关口（2026-11-17，维护者的决定）：**身份编号统一用 base32。** 推荐第 3 条原写“编号是 base64url 指纹（43 字符），同时用作 `kid`”；改为：

- 身份编号 = RFC 7638 指纹（SHA-256）那 32 字节的 base32（RFC 4648 字母表，小写，无填充，52 字符），与 identity-card.md 第 3 节一致；JWS 头里的 `kid` 就是它。
- base64url 指纹只出现在 RFC 9278 的 URN 里（令牌的 `iss` / `sub` / `aud`），因为 RFC 9278 规定 URN 用 base64url。
- 验证方只认 base32 的 `kid`（自己签的、联系人签的都一样）；同一把钥匙的 base64url 指纹写在 `kid` 里拒绝。实施见 ADR-120 的关口决定一节。
