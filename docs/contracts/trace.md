# 链路号契约

版本：0.1　状态：草稿，待维护者评审
修订：0.1（2026-11-16）初稿。 0.1.1（2026-11-17，P4-04 安全审查 L-8）第 7 节：次数按调用方 × 链路号数，链路号和深度是调用方自报的。 0.1.2（2026-11-17，P4-08，ADR-127）第 3、5 节：一轮的深度记在 `jobs.depth`，答复唤醒沿用链路号和发起那一轮的深度；本机发出的调用记在 `a2a_calls`，与收到的一起数。
共用范围：几家共用。外部的任务与聊天系统、以插件接入的组织内部集成发起或转交调用时照它传。

依据：设计里的“链路号”与“去调用别的智能体”、“可追溯”原则（跨 Daisy 的调用带同一个链路号）、P1-11、P4-08；设计约定“链路深度和次数的上限：沿用现有聊天模块里的数值”。

---

## 1. 是什么

链路号是**一次用户动作**的编号。这次动作引起的所有执行、所有跨系统调用都带同一个链路号；两边的日志和审计都记它；也用它数调用深度，防止两个 AI 互相调用停不下来。

## 2. 格式

照 W3C Trace Context（`traceparent`）：

```
traceparent: 00-<trace-id>-<parent-id>-<flags>
例：         00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-00
```

| 部分 | 格式 | 本契约里的意思 |
| --- | --- | --- |
| 版本 | `00` | |
| `trace-id` | 32 位小写十六进制（16 字节随机数），不能全为 0 | **链路号本身**。审计里记的就是它 |
| `parent-id` | 16 位小写十六进制，不能全为 0 | 这一跳的编号。每发出一次调用新生成一个。只用于对照日志，不参与任何判断 |
| `flags` | 两位十六进制 | 本契约不用，发 `00`，收到什么都接受 |

选它的理由：现成的标准，和常见的可观测性工具直接对得上；CloudEvents 的分布式追踪扩展也用它（events.md）。

收到不合格的 `traceparent`（长度不对、不是十六进制、全 0）：照 W3C 的规定当作没有，自己新起一个链路号，并在日志里记一条警告。

## 3. 什么时候新起，什么时候沿用

| 情况 | 链路号 | 深度 |
| --- | --- | --- |
| 主人在网页、命令行、手机上做一个动作（发消息、批准…） | 新起。请求带了 `traceparent` 就用它的 | 0 |
| 定时器、周期任务、后台命令的结果唤醒 AI | 新起 | 0 |
| 外部系统经插件挂点唤醒会话（P1-10） | 事件或请求带了就沿用，否则新起 | 带了就沿用，否则 0 |
| AI 在一轮里调用别的智能体 | 沿用这一轮的 | 这一轮的深度 + 1 |
| 收到一次 A2A 调用 | 沿用调用方传来的；没传就新起 | 调用方传来的值；没传按 1 |
| 被调用方的答复回来，唤醒发起调用的 AI | 沿用 | 不变（是原来那一层的继续，不是更深一层） |
| 调用方补充信息（“需要输入”之后再发一条） | 沿用调用方传来的 | 同一个任务的深度不变 |

“这一轮的链路号”：一轮由什么引起，就沿用那件事的链路号。

实现（P4-08，ADR-127）：一轮的链路号和深度记在 `jobs.trace` / `jobs.depth`；外来任务开的一轮要写上那次调用的深度（P4-05 / P4-07 的执行方），答复唤醒的一轮写发起调用那一轮的（`wakes.trace` / `wakes.depth`）。

## 4. 怎么传

**HTTP 头。** 任何一方向别人发 HTTP 请求（本机接口、A2A、事件出口），都可以带 `traceparent` 请求头。只有链路号，没有深度。

**A2A 消息的 metadata。** 跨智能体调用时，深度必须随消息走，所以放进消息的 `metadata`，用一个可选扩展的 URI 做键（A2A 规范：扩展的数据放进 `metadata`，以扩展 URI 为键）：

```json
"metadata": {
  "https://quantgrail.github.io/a2a-ext/trace/v1": {
    "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-b7ad6b7169203331-00",
    "depth": 2
  }
}
```

- 扩展 URI 暂定。被调用方在 agent 名片里把它声明为 `required: false` 的扩展（a2a-usage.md 第 8 节）。
- `depth` 是**这次调用将要引起的那一轮的深度**，即调用方这一轮的深度加 1。
- 调用方同时带 `traceparent` 请求头（链路号相同），并在 `A2A-Extensions` 请求头里列出这个 URI。
- 两处都有而链路号不一样时，以 metadata 为准。
- 不认识这个扩展的第三方客户端什么都不带：被调用方新起链路号，深度按 1。

## 5. 上限

| 上限 | 值 | 出处（旧版代码，已删除） |
| --- | --- | --- |
| 深度 | **8**。深度 8 的那一轮还可以执行，要产生深度 9 的调用时拒绝 | `services/server/src/collaboration.ts` 第 644–646 行：`depth = parent.depth + 1`，`depth > 8` 时报“协作链已达 8 层” |
| 次数 | **64**。同一个链路号下第 65 次调用拒绝 | 同文件第 651–658 行：`calls + 新增 > 64` 时报“本次协作已达 64 次调用”；第 7587–7593 行重新投递时同样按 64 判断 |

这两个数是旧聊天模块里“同一条消息链”的上限，原样沿用到“同一个链路号”（设计的默认做法）。集中配置见 limits.md。

**谁来检查**

- **调用方**发出之前检查：自己这一轮的深度 + 1 > 8，或这个链路号在本机已经用了 64 次，就不发，给 AI 一个工具错误，说明“调用链已达上限，请汇总现有结果，交由主人决定是否继续”。
- **被调用方**收到时检查：`depth` > 8，或这个链路号在本机已经用了 64 次，就把任务置为“已拒绝”，说明原因（a2a-usage.md 第 9 节）。

**次数怎么数。** 每一方只数自己看到的：本机发出的和本机接受的、带这个链路号的调用，合起来不超过 64。一条链路分叉到好几个系统时，没有一处能看到全局的总数，所以这是每一方各自的上限，不是全局的。深度则是全局一致的，因为它随消息传下去。

## 6. 记在哪里

- 审计：每条记录带 `trace_id`（32 位十六进制）和 `depth`（P1-11）。
- 事件：`traceparent` 属性（events.md）。
- 日志：带 `trace_id`。

## 7. 防得住什么，防不住什么

深度和次数防的是**守约的**AI 之间无意中的循环。链路号和深度都是调用方自报的；被调用方按“调用方 × 链路号”数次数（P4-04 审查 L-8），别人用同一个链路号不会占掉你的次数，你换个链路号也就重新数——这不是防线。深度由调用方自报，一个不守约的调用方可以把 `depth` 填成 1。防恶意调用靠的是互认、调用授权、并发上限和撤销，不是链路号。
